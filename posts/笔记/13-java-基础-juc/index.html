基础知识#

进程 vs 线程#

进程（Process）#

在计算机科学中，进程是指正在运行中的程序实例。每个进程都是一个独立的执行单元，拥有自己的内存空间和系统资源。一个进程可以包含多个线程，是程序执行的基本单位。

线程（Thread）#

线程是进程中的一个独立执行路径，是操作系统能够进行运算调度的最小单位。一个进程至少包含一个线程，称为主线程。 多个线程可以在同一进程内并发执行，共享进程的资源，每个线程有自己的执行栈和局部变量。

对比维度进程线程
资源分配拥有独立的内存空间与系统资源，进程间通信复杂，需借助管道、消息队列等专用通信机制共享所属进程的内存空间和大部分资源，线程间通信更简单、高效
执行方式独立执行，拥有专属地址空间，进程之间相互独立、互不干扰依附进程存在，同一进程内的多个线程可并发执行，共用进程资源
开销创建、销毁开销大，需为其分配独立的内存空间和系统资源创建、销毁开销小，因共享进程的资源，无需额外分配核心资源
并发性作为独立执行单元，不受其他进程影响，运行安全性较高因共享进程资源，并发执行时需处理同步、互斥问题，运行安全性较低

同步 vs 异步#

同步（Sync）#

  • 定义
    • 任务按顺序执行，前一个任务完成前，后一个任务必须等待。
  • 特点
    • 线程阻塞：当前线程需等待同步代码执行完毕。
    • 线程安全：通过锁机制避免数据竞争。
    • 性能影响：可能降低并发效率。
  • 例如
    • B/S模式中的表单提交，具体过程是：客户端提交请求->等待服务器处理->处理完毕返回，在这个过程中客户端（浏览器）不能做其他事。

异步（Async）#

  • 定义
    • 任务可并发执行，调用后立即返回，无需等待结果。
  • 特点
    • 非阻塞：主线程继续执行后续任务。
    • 复杂度：需处理回调或轮询结果（如 Future.get()）。
    • 性能优势：提升资源利用率和响应速度。
  • 例如：对于通知调用者的三种方式，具体如下：
    • 状态：即监听被调用者的状态（轮询），调用者需要每隔一定时间检查一次，效率会很低。
    • 通知：当被调用者执行完成后，发出通知告知调用者，无需消耗太多性能。
    • 回调：与通知类似，当被调用者执行完成后，会调用调用者提供的回调函数。
维度同步异步
执行顺序顺序执行，严格依赖前任务结果并发执行，不依赖前任务结果
线程行为调用线程阻塞等待调用线程立即返回，不阻塞
实现复杂度简单（直接加锁）较高（需处理回调、Future 等）
适用场景数据敏感操作（如银行交易）耗时操作（如 I/O、批量处理）
性能影响可能降低并发效率提高吞吐量和响应速度
典型工具synchronized、LockCompletableFuture、线程池

并发 vs 并行#

并发#

  • 定义
    • 指两个或多个事件在同一个时间段内发生
  • 特点
    • 执行方式：单 CPU 下通过 “时间片轮转 + 上下文切换” 实现任务交替，宏观呈现 “同时执行”，微观实际交替进行
    • 硬件依赖：无需多核硬件，单 CPU 即可支持
    • 核心目标：提升单 CPU 的资源利用率，避免资源闲置
    • 关键要求：需保障 “可见性、原子性、有序性” 这三要素，避免数据竞争等问题
  • 例如
    • 单 CPU 电脑同时打开浏览器浏览网页、音乐播放器播放歌曲：宏观上两个程序 “同时运行”，实际 CPU 通过快速切换时间片，交替处理两个程序的任务
  • 并发三要素
    • 可见性：一个线程对共享变量的修改，另外一个线程能够立刻看到。
    • 原子性：即一个操作或者多个操作 要么全部执行并且执行的过程不会被任何因素打断，要么就都不执行。
    • 有序性：即程序执行的顺序按照代码的先后顺序执行。

并行#

  • 定义
    • 指两个或多个事件在同一时刻发生（同时发生）。
  • 特点
    • 执行方式：多 CPU / 多核处理器下，多个任务在不同硬件核心上独立执行，宏观与微观均为 “同时进行”
    • 硬件依赖：依赖多 CPU、多核等硬件条件，单 CPU 无法实现
    • 核心目标：利用多硬件核心的算力，缩短多个任务的总执行时间
    • 资源利用：减少上下文切换开销，充分发挥多核心的性能优势
  • 例如
    • 多核 CPU 电脑同时进行视频渲染和文件压缩：视频渲染任务在核心 1 执行，文件压缩任务在核心 2 执行，两个任务在同一时刻真正同时运行
对比维度并发并行
核心概念同一时间段内，多个任务交替执行（宏观 “同时”，微观交替）同一时刻，多个任务在不同硬件核心上同时执行（宏观 + 微观均 “同时”）
执行方式单 CPU 下通过 “时间片轮转 + 上下文切换” 实现任务交替多 CPU / 多核下，多个任务在不同核心上独立执行，无（或少）上下文切换
硬件依赖无需多核，单 CPU 即可支持依赖多 CPU、多核处理器等硬件条件
核心目标提高单 CPU 的资源利用率，避免资源闲置利用多硬件核心，缩短多个任务的总执行时间
典型场景单线程处理多个用户的网络请求、单 CPU 系统的多任务调度多核 CPU 同时渲染多帧图像、分布式系统多节点并行计算大数据

阻塞 vs 非阻塞#

阻塞#

  • 定义
    • 指线程在执行过程中，因等待某个资源就绪或事件完成，暂时放弃 CPU 执行权，进入「阻塞状态」，直到等待的条件满足（如资源就绪、等待超时、被其他线程唤醒），才会被唤醒并重新争抢 CPU 时间片继续执行。
  • 特点
    • 线程状态：进入阻塞态，期间不占用 CPU 计算资源，仅占用内存等系统资源
    • 锁行为：分场景决定是否释放锁（wait()会释放对象锁，sleep()、join()、同步阻塞不会释放已持有的锁）
    • 执行特性：等待期间无法执行任何业务逻辑，需被动等待条件满足后才能恢复执行
    • 触发场景：常见于资源等待（如 IO 操作、锁竞争）、主动休眠（sleep()）、线程等待（join()）、条件等待（wait()）
  • 例如
    • 线程调用Thread.sleep(1000)后进入阻塞状态，休眠期间不占用 CPU，1 秒后自动唤醒重新争抢时间片
    • 线程在同步代码块中等待获取锁时，因锁被其他线程持有，进入阻塞状态，直到锁释放后被唤醒
    • 线程调用Object.wait()后释放对象锁并进入阻塞状态，直到其他线程调用notify()/notifyAll()才被唤醒
    • 同步 IO 读取大文件时，线程阻塞等待磁盘数据加载到内存，期间无法执行其他操作

非阻塞#

  • 定义
    • 指线程在执行过程中，即使所需资源未就绪或事件未完成，也不会放弃 CPU 执行权，不会进入阻塞状态，而是立即返回执行结果（如资源未就绪的标识、失败信息等），并可继续执行后续业务逻辑，无需被动等待。
  • 特点
    • 线程状态：始终处于「就绪状态」或「运行状态」，不进入阻塞态
    • CPU 占用：会持续占用 CPU 资源（即使资源未就绪，也可能通过轮询等方式重试，不释放 CPU）
    • 执行特性：无需被动等待，立即返回结果，可自主决定后续重试策略或执行其他逻辑
    • 实现复杂度：相对较高，需手动处理资源未就绪的场景，避免无效轮询浪费 CPU 资源
  • 例如
    • Java 原子类（AtomicInteger）的compareAndSet(CAS)操作：当更新失败时（资源被其他线程修改），不会阻塞等待，而是立即返回false，可由业务逻辑决定是否重试
    • 非阻塞 IO（NIO）：线程发起 IO 操作后，无需等待数据传输完成，立即返回并执行其他逻辑，当数据就绪后通过事件通知机制进行处理
    • 线程轮询检查打断标记：while (!Thread.currentThread().isInterrupted())循环中，每次检查后立即返回结果，不会阻塞，若标记为true则退出循环，否则继续执行业务逻辑
    • 分布式缓存查询（如 Redis）：当缓存未命中时，线程不会阻塞等待数据库查询结果，而是立即发起异步数据库请求，同时继续处理其他任务，待数据库结果返回后再进行后续处理
对比维度阻塞非阻塞
核心概念线程因等待资源/事件就绪，暂时放弃CPU执行权，进入阻塞状态，需被动等待条件满足后才能恢复执行线程即使所需资源/事件未就绪，也不放弃CPU执行权，不进入阻塞状态，立即返回结果，可自主执行后续逻辑
线程状态进入阻塞态（包含BLOCKED、WAITING、TIMED_WAITING三种细分状态）始终处于就绪状态或运行状态，不进入任何阻塞态
CPU占用等待期间不占用CPU计算资源，仅占用内存等系统资源持续占用CPU资源（若资源未就绪，可能通过轮询重试，造成CPU无效消耗）
锁行为分场景决定是否释放锁：wait()会释放对象锁；sleep()、join()、同步锁竞争阻塞不会释放已持有的锁通常无需持有锁（如CAS操作），不存在锁释放的相关逻辑，避免锁竞争问题
执行特性等待期间无法执行任何业务逻辑，需被动等待（资源就绪/超时/被唤醒）后才能恢复无需被动等待，立即返回执行结果（成功/资源未就绪标识），可自主决定重试策略或执行其他任务
实现复杂度实现简单，无需手动处理资源未就绪的场景，由JVM/系统自动管理线程状态切换实现复杂度较高，需手动处理资源未就绪的场景，需优化重试策略（如限制轮询次数）避免CPU浪费

线程的生命周期#

操作系统层面#

分为五种状态

  1. 初始状态 线程被创建，但尚未启动。
  2. 可运行状态(就绪状态) 线程已经启动，等待CPU的调度。
  3. 运行状态 线程获得CPU时间片，正在执行。
  4. 阻塞状态 线程正在等待某种条件（如I/O操作）完成。
  5. 终止状态 线程执行完成或抛出异常后的状态

java api层面#

分为六种状态

  1. 新建（NEW） 线程对象已创建（new Thread()），但尚未调用start()方法。
  2. 可运行（RUNNABLE）& 运行状态（Running）
    • 线程已启动（调用start()），正在JVM中运行，但可能在等待操作系统分配CPU时间片。
    • 线程获得CPU时间片，正在执行run()方法中的代码。
  3. 阻塞（BLOCKED） 线程等待获取锁（如synchronized块）时的状态
  4. 等待状态（WAITING） 线程调用wait()、join()或LockSupport.park()后进入的状态，需显式唤醒。
  5. 超时等待（TIMED_WAITING） 线程调用Thread.sleep()、wait(timeout)、join(timeout)等带超时参数的方法后进入的状态。
  6. 终止（TERMINATED） 线程执行完毕（run()方法正常返回）或因未捕获的异常终止。

上下文切换#

单核CPU在同一时刻只能执行一个线程。为了让用户感觉多个线程在同时执行，CPU需要通过分配时间片来轮流执行各个线程。当一个线程的时间片用完或被高优先级线程抢占时，就需要保存当前线程的状态（如程序计数器、寄存器信息），然后加载另一个线程的状态，这个过程就是上下文切换。频繁的上下文切换会消耗大量资源。

    • 通常需要重写Runnable接口或Thread类的run()方法来定义业务逻辑，直接调用run()仅为普通方法执行，不会创建新线程

3. yield()#

  • 参数：无参数
  • 含义：static方法，线程礼让机制；当前正在执行的线程主动放弃CPU时间片，从「运行状态」回到「就绪状态」，与其他就绪状态的线程重新争抢CPU时间片；礼让不保证一定成功，CPU仍可能再次调度该线程

4. sleep(long millis) / sleep(long millis, int nanos)#

  • 参数：
    1. long millis：必传参数，休眠时间（单位：毫秒）
    2. int nanos：可选参数，额外休眠时间（单位：纳秒，取值范围0-999999）
  • 含义：static方法，让当前线程进入「阻塞状态」，休眠指定时间后自动唤醒，回到「就绪状态」重新争抢CPU时间片；休眠期间线程不会释放已持有的锁，且可被interrupt()方法打断（打断后抛出InterruptedException异常）
  • 示例：

5. join() / join(long millis)#

  • 参数：
    1. 无参join()：无限等待，直到目标线程执行完毕
    2. long millis：指定等待时间（单位：毫秒），超时后不再等待
  • 含义：调用该方法的「调用者线程」会进入「阻塞状态」，等待目标线程执行完毕（无参）或等待指定时间（有参）后，自动唤醒并回到「就绪状态」；常用于控制线程执行顺序（如主线程等待子线程执行完成后再继续）
  • 示例：

6. isInterrupted()#

  • 参数：无参数
  • 含义：获取目标线程的「打断标记」，返回boolean值（true=被打断，false=未被打断）；调用后不会修改打断标记的状态（标记保持原值不变）
  • 示例：

7. interrupt()#

  • 参数：无参数
  • 含义：打断目标线程，具体行为分两种场景：
    1. 若线程处于「休眠（sleep）」、「等待（wait）」、「阻塞（join）」状态，会抛出InterruptedException异常，且自动重置打断标记为false
    2. 若线程处于正常运行状态，仅修改打断标记为true，不会终止线程，需线程自行判断标记并退出
  • 示例：

8. interrupted()#

  • 参数：无参数
  • 含义：static方法（纠正：此前表格中标记为「否」有误，实际为static），获取「当前执行线程」的打断标记，返回boolean值；调用后会清空（重置）打断标记为false（无论原标记是true还是false，调用后均重置）
  • 示例：

9. stop()#

  • 参数：无参数
  • 含义：强制终止目标线程运行，已废弃（不推荐使用）；强制停止线程会导致线程持有的锁、资源无法正常释放，造成资源泄露、数据不一致等问题

10. suspend()#

  • 参数：无参数
  • 含义：挂起目标线程，使线程从「运行状态」进入「阻塞状态」，已废弃（不推荐使用）；挂起线程时不会释放已持有的锁，容易造成死锁，且无法感知线程挂起状态

11. resume()#

  • 含义：恢复被suspend()方法挂起的线程，使线程从「阻塞状态」回到「就绪状态」，已废弃（不推荐使用）；需与suspend()配合使用，存在线程安全问题（如线程被挂起后，未及时恢复会导致死锁）

ThreadPoolExecutor#

介绍#

线程池是java并发最重要的一个知识点，也是难点，是实际应用最广泛的。

线程的资源很宝贵，不可能无限的创建，必须要有管理线程的工具，线程池就是一种管理线程的工具，java开发中经常有池化的思想，如 数据库连接池、Redis连接池等。

预先创建好一些线程，任务提交时直接执行，既可以节约创建线程的时间，又可以控制线程的数量。

线程池的好处

  1. 降低资源消耗，通过池化思想，减少创建线程和销毁线程的消耗，控制资源
  2. 提高响应速度，任务到达时，无需创建线程即可运行
  3. 提供更多更强大的功能，可扩展性高

主要流程#

线程池创建、接收任务、执行任务、回收线程的步骤

  1. 创建线程池后，线程池的状态是Running，该状态下才能有下面的步骤
  2. 提交任务时，线程池会创建线程去处理任务
  3. 当线程池的工作线程数达到corePoolSize时，继续提交任务会进入阻塞队列
  4. 当阻塞队列装满时，继续提交任务，会创建救急线程来处理
  5. 当线程池中的工作线程数达到maximumPoolSize时，会执行拒绝策略
  6. 当线程取任务的时间达到keepAliveTime还没有取到任务，工作线程数大于corePoolSize时，会回收该线程

构造方法#

  • corePoolSize 核心线程数，线程池中始终存活的线程数。
  • maximumPoolSize 最大线程数，线程池中允许的最大线程数，当线程池的任务队列满了之后可以创建的最大线程数。
  • keepAliveTime 最大线程数可以存活的时间，当线程中没有任务执行时，最大线程就会销毁一部分，最终保持核心线程数量的线程。
  • unit 单位是和参数 3 存活时间配合使用的，合在一起用于设定线程的存活时间。
    • TimeUnit.DAYS：天
    • TimeUnit.HOURS：小时
    • TimeUnit.MINUTES：分
    • TimeUnit.SECONDS：秒
    • TimeUnit.MILLISECONDS：毫秒
    • TimeUnit.MICROSECONDS：微妙
    • TimeUnit.NANOSECONDS：纳秒
  • workQueue 一个阻塞队列，用来存储线程池等待执行的任务，均为线程安全。它一般分为直接提交队列、有界任务队列、无界任务队列、优先任务队列几种
    • ArrayBlockingQueue一个由数组结构组成的有界阻塞队列。
    • LinkedBlockingQueue一个由链表结构组成的有界阻塞队列。
    • SynchronousQueue一个不存储元素的阻塞队列，即直接提交给线程不保持它们。
    • PriorityBlockingQueue一个支持优先级排序的无界阻塞队列。
    • DelayQueue一个使用优先级队列实现的无界阻塞队列，只有在延迟期满时才能从中提取元素
    • LinkedTransferQueue一个由链表结构组成的无界阻塞队列。与SynchronousQueue类似，还含有非阻塞方法。
    • LinkedBlockingDeque一个由链表结构组成的双向阻塞队列。 较常用的是 LinkedBlockingQueue 和 Synchronous，线程池的排队策略与 BlockingQueue 有关
  • threadFactory 线程工厂，主要用来创建线程。
  • handler 拒绝策略，拒绝处理任务时的策略，系统提供了 4 种。
    • AbortPolicy拒绝并抛出异常，丢弃任务并抛出 RejectedExecutionException 异常 （默认策略）
    • CallerRunsPolicy丢弃任务，但是不抛出异常。可能导致无法发现系统的异常状态
    • DiscardOldestPolicy抛弃队列头部（最旧）的一个任务，丢弃队列最前面的任务，然后重新提交被拒绝的任务
    • DiscardPolicy忽略并抛弃当前任务，丢弃任务，但是不抛出异常。可能导致无法发现系统的异常状态

ForkJoinPool#

介绍#

fork/join 框架在 Java 7 中引入。它基于分而治之的思想，通过尝试利用所有可用处理器内核来帮助加速并行计算。广泛用在java8的parallelStream和CompletableFuture中。

适用于：

  • 大数据处理：数组排序、矩阵运算（参考案例：百万级数据求和效率提升 3 倍）
  • 分治算法：快速排序、归并排序、斐波那契数列计算。
  • 并行流基础：Java 8 的parallelStream()底层实现

其主旨是将大任务分成若干小任务，之后再并行对这些小任务进行计算，最终汇总这些任务的结果，得到最终的结果。

此外，ForkJoinPool采取工作窃取算法，以避免工作线程由于拆分了任务之后的join等待过程。 这样处于空闲的工作线程将从其他工作线程的队列中主动去窃取任务来执行。 这里涉及到的两个基本知识点是分治法和工作窃取。 这只是一个简化版本的Fork-Join，实际上我们在日常工作中的应用可能比这要复杂很多。但是基本原理类似。 这样就将一个大的任务，通过fork方法不断拆解，直到能够计算为止，之后，再将这些结果用join合并。 这样逐次递归，就得到了我们想要的结果。这就是再ForkJoinPool中的分治法。

工作窃取算法#

由于线程处理不同任务的速度不同，这样就可能存在某个线程先执行完了自己队列中的任务的情况，这时为了提升效率，我们可以让该线程去“窃取”其它任务队列中的任务，这就是所谓的工作窃取算法。

当工作线程空闲时，它可以从其他工作线程的任务队列中”窃取”任务。

以充分利用工作线程的计算能力，减少线程由于获取不到任务而造成的空闲浪费。

在ForkJoinPool中，工作任务的队列都采用双端队列Deque容器。

在通常使用队列的过程中，我们都在队尾插入，而在队头消费以实现FIFO。

而为了实现工作窃取。一般我们会改成工作线程在工作队列上LIFO，而窃取其他线程的任务的时候，从队列头部取获取。示意图如下： 工作线程worker1、worker2以及worker3都从taskQueue的尾部popping获取task，而任务也从尾部Pushing，当worker3队列中没有任务的时候，就会从其他线程的队列中取stealing，这样就使得worker3不会由于没有任务而空闲。

实现原理#

在JUC中，实现Fork-join框架有两个类，分别是ForkJoinPool和提交的任务抽象类ForkJoinTask。

核心类关系图

  • ForkJoinPool：ExecutorService 的实现类，负责工作线程的管理、任务队列的维护，以及控制整个任务调度流程；
  • ForkJoinTask：Future 接口的实现类，fork 是其核心方法，用于分解任务并异步执行；而 join 方法在任务结果计算完毕之后才会运行，用来合并或返回计算结果；
  • ForkJoinWorkerThread：Thread 的子类，作为线程池中的工作线程（Worker）执行任务；
  • WorkQueue：任务队列，用于保存任务；

ForkJoinPool#

ForkJoinPool 的主要工作如下：

  1. 接受外部任务的提交（外部调用 ForkJoinPool 的invoke/execute/submit方法提交任务）；
  2. 接受 ForkJoinTask 自身fork出的子任务的提交；
  3. 任务队列数组（WorkQueue[]）的初始化和管理；
  4. 工作线程（Worker）的创建/管理。

提交任务的方法：invoke、execute、submit，它们的主要区别在于任务的执行方式上。

  • 通过invoke方法提交的任务，调用线程直到任务执行完成才会返回，也就是说这是一个同步方法，且有返回结果；
  • 通过execute方法提交的任务，调用线程会立即返回，也就是说这是一个异步方法，且没有返回结果；
  • 通过submit方法提交的任务，调用线程会立即返回，也就是说这是一个异步方法，且有返回结果（返回 Future 实现类，可以通过 get 获取结果）。

ForkJoinPool 对象的构建有两种方式：

  1. 通过 3 种构造器的任意一种进行构造；
  2. 通过ForkJoinPool.commonPool()静态方法构造。

ForkJoinTask#

ForkJoinTask 实现了 Future 接口，是一个异步任务，我们在使用 Fork/Join 框架时，一般需要使用线程池来调度任务，线程池内部调度的其实都是 ForkJoinTask 任务（即使提交的是一个 Runnable 或 Callable 任务，也会被适配成 ForkJoinTask）。

除了 ForkJoinTask，Fork/Join 框架还提供了两个它的抽象实现，我们在自定义 ForkJoin 任务时，一般不会直接继承ForkJoinTask，只要继承它的子类即可：

  • RecursiveAction：表示具有返回结果的 ForkJoin 任务
  • RecursiveTask：表示没有返回结果的 ForkJoin 任务
  • CountedCompleter：在任务完成执行后，触发自定义的钩子函数。

主要方法：

  • fork()：异步执行任务
  • join()：等待任务完成并获取结果
  • compute()：子类必须实现的方法，包含任务的具体计算逻辑

ForkJoinWorkerThread#

Fork/Join 框架中，每个工作线程（Worker）都有一个自己的任务队列（WorkerQueue）， 所以需要对一般的 Thread 做些特性化处理，J.U.C 提供了ForkJoinWorkerThread类作为 ForkJoinPool 中的工作线程：

ForkJoinWorkerThread 在构造过程中，会保存所属线程池信息和与自己绑定的任务队列信息。同时，它会通过 ForkJoinPool 的registerWorker方法将自己注册到线程池中。

线程池中的每个工作线程（ForkJoinWorkerThread）都有一个自己的任务队列（WorkQueue），工作线程优先处理自身队列中的任务（LIFO 或 FIFO 顺序，由线程池构造时的参数 mode 决定），自身队列为空时，以 FIFO 的顺序随机窃取其它队列中的任务。

WorkQueue#

任务队列（WorkQueue）是 ForkJoinPool 与其它线程池区别最大的地方，在 ForkJoinPool 内部，维护着一个WorkQueue[]数组.

WorkQueue作为 ForkJoinPool 的内部类，表示一个双端队列。双端队列既可以作为栈使用(LIFO)，也可以作为队列使用(FIFO)。

ForkJoinPool 的“工作窃取”正是利用了这个特点，当工作线程从自己的队列中获取任务时，默认总是以栈操作（LIFO）的方式从栈顶取任务；当工作线程尝试窃取其它任务队列中的任务时，则是 FIFO 的方式。

1. 优先使用 ThreadPoolExecutor 的场景#

ThreadPoolExecutor 是 “通用型选手”，适合任务独立、无依赖的场景，尤其是 IO 密集型任务（线程常处于等待状态）。

典型场景：#
  • IO 密集型任务：如 HTTP 接口调用、数据库查询、文件读写、消息队列消费等。
    • 例：批量查询数据库中的 1000 条数据（每条查询独立）、异步发送 100 封邮件（每封发送独立）。
    • 原因：IO 任务中线程大部分时间在等待（如等待数据库响应、网络传输），ThreadPoolExecutor 可通过调整线程数（通常大于 CPU 核心数）提高吞吐量，且独立任务无需拆分合并，无额外开销。
  • 简单 CPU 密集型任务：多个独立的计算任务，无需协作。
    • 例：批量计算 100 个数字的阶乘（每个计算独立）、对 100 张图片进行独立压缩（无依赖）。
    • 原因：任务简单无需拆分，ThreadPoolExecutor 的共享队列调度足够高效，且避免了 ForkJoinPool 拆分合并的额外开销。
  • 需要灵活配置的场景：如需要自定义队列（有界队列避免内存溢出）、拒绝策略（任务满时丢弃 / 重试）、线程工厂（自定义线程名称、优先级）等。
    • 例：高并发接口的异步处理（用有界队列 + 拒绝策略保护系统）。

2. 优先使用 ForkJoinPool 的场景#

ForkJoinPool 是 “分治专家”，适合任务可拆分、有依赖、计算量大的 CPU 密集型场景，核心是通过拆分任务充分利用多核 CPU 资源。

典型场景：#
  • 复杂 CPU 密集型计算：大任务可拆分为多个子任务，子任务计算完成后需合并结果。
    • 例 1：大规模数据排序（如并行归并排序）、矩阵乘法、斐波那契数列计算（递归拆分）；
    • 例 2：统计 1000 万条数据的总和 / 平均值（拆分数据块，分别计算后求和）；
    • 例 3：文件目录遍历（遍历一个大目录下的所有文件，拆分到子目录，最终汇总文件列表）。
  • 任务拆分后可并行执行：子任务无状态、无共享资源，可独立计算，合并结果的开销小于并行带来的收益。
核心要求：#
  • 任务必须可拆分（拆分到最小粒度后执行效率最高，粒度太小会增加拆分合并开销，粒度过大则无法充分利用多核）；
  • 计算密集型（线程大部分时间在执行计算，无频繁等待，适合工作窃取机制发挥作用）。

ThreadLocal#

介绍#

ThreadLocal是一个将在多线程中为每一个线程创建单独的变量副本的类;

当使用ThreadLocal来维护变量时, ThreadLocal会为每个线程创建单独的变量副本, 避免因多线程操作共享变量而导致的数据不一致的情况。

原理#

主要是用到了Thread对象中的一个ThreadLocalMap类型的变量threadLocals, 负责存储当前线程的关于Connection的对象, dbConnectionLocal(以上述例子中为例) 这个变量为Key, 以新建的Connection对象为Value; 这样的话, 线程第一次读取的时候如果不存在就会调用ThreadLocal的initialValue方法创建一个Connection对象并且返回;

其实就是在set()、get()方法的具体实现

具体关于为线程分配变量副本的代码如下:

  • 首先获取当前线程对象t, 然后从线程t中获取到ThreadLocalMap的成员属性threadLocals
  • 如果当前线程的threadLocals已经初始化(即不为null) 并且存在以当前ThreadLocal对象为Key的值, 则直接返回当前线程要获取的对象(本例中为Connection);
  • 如果当前线程的threadLocals已经初始化(即不为null)但是不存在以当前ThreadLocal对象为Key的的对象, 那么重新创建一个Connection对象, 并且添加到当前线程的threadLocals Map中,并返回
  • 如果当前线程的threadLocals属性还没有被初始化, 则重新创建一个ThreadLocalMap对象, 并且创建一个Connection对象并添加到ThreadLocalMap对象中并返回。

如果存在则直接返回很好理解, 那么对于如何初始化的代码又是怎样的呢?

  • 首先调用我们上面写的重载过后的initialValue方法, 产生一个Connection对象

  • 继续查看当前线程的threadLocals是不是空的, 如果ThreadLocalMap已被初始化, 那么直接将产生的对象添加到ThreadLocalMap中, 如果没有初始化, 则创建并添加对象到其中;

InheritableThreadLocal#

介绍#

ThreadLocal的升级版，jdk原生，实现了父子线程之间的数据传递。

原理#

重新开辟一块空间（InheritableThreadLocal）用于存储父子线程共用的数据隔离空间。重写了ThreadLocal的三个方法，当创建新线程的时候，将父线程的ThreadLocal值拷贝到子线程。

局限性#

  • 只支持创建新线程时的值传递
  • 线程池场景下不适用（线程复用）

示例#

TransmittableThreadLocal#

介绍#

TransmittableThreadLocal（TTL）是阿里开源的一个线程间数据传递解决方案，解决了InheritableThreadLocal在线程池场景下的问题。 核心特性

  • 支持线程池场景下的值传递
  • 支持任务执行前的自定义逻辑
  • 支持任务执行后的自定义逻辑
  • 兼容InheritableThreadLocal

结构#

  • TransmittableThreadLocal：继承自InheritableThreadLocal
  • TtlRunnable/TtlCallable：装饰器模式包装Runnable和Callable
  • Transmitter：提供capture/replay/restore机制

原理#

TTL的核心思想是”捕获-传递-恢复”：

  1. 捕获（Capture）：在任务提交到线程池时，捕获当前线程的所有TTL变量
  2. 传递（Transmit）：将捕获的值传递给线程池中的线程
  3. 恢复（Replay）：线程池中的线程在执行任务前，将TTL值恢复
  4. 回滚（Restore）：任务执行完成后，恢复线程原来的TTL值

性能考虑#

  • TTL会带来一定的性能开销（约5%）
  • 高并发场景下应评估是否必要
  • 考虑使用更轻量的解决方案（如方法参数传递）

方法含义
tryLock()尝试获取锁，但不会导致线程进入等待队列。如果锁可用，则立即获取锁并返回true。如果锁不可用，则立即返回false，而不会等待锁释放。此方法可用于避免线程长时间等待锁。
lock()和unlock()lock()方法用于获取锁。如果锁可用，则当前线程将获得锁。如果锁不可用，则当前线程将进入等待队列，直到锁变为可用。当线程成功获取锁之后，需要在finally块中调用unlock()方法释放锁，以确保其他线程可以获取锁。
getHoldCount()当前线程调用 lock() 方法的次数。
getQueueLength()当前正在等待获取 Lock 锁的线程的估计数。
getWaitQueueLength(Condition condition)当前正在等待状态的线程的估计数，需要传入 Condition 对象。
lockInterruptibly()如果当前线程未被中断，则获取该锁定，如果已经被中断则出现异常。
isLocked()查询此锁定是否由任意线程保持。
isFair()判断当前 Lock 锁是不是公平锁。
isHeldByCurrentThread()查询当前线程是否保持此锁定。
hasWaiters(Condition condition)查询是否有线程正在等待与 Lock 锁有关的 Condition 条件。
hasQueuedThread(Thread thread)查询指定的线程是否正在等待获取 Lock 锁。
